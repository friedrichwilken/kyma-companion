---

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### 📋 Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### 🔐 Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider | Custom auth logic (e.g., OAuth2 Proxy) |

---

### 📄 Example APIRule YAMLs

#### 1. Open Endpoint (`noAuth`)
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service   # short host name; full domain is auto-appended from the Gateway
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service       # Kubernetes Service name
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

#### 2. JWT-Protected Endpoint (`jwt`) — Recommended
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: "https://my-identity-provider.com"
            jwksUri: "https://my-identity-provider.com/.well-known/jwks.json"
```

---

### 🛠️ Steps to Expose Your Endpoint

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply your APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Verify the APIRule is ready:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   # Expected output: Ready
   ```

4. **Access your endpoint:**
   Your service will be available at:
   `https://<host>.<cluster-domain>`

---

### 💡 Advanced Capabilities

- **Multiple workloads on the same host** — Route traffic to different Services based on paths/methods.
- **Short host names** — Use just a name (e.g., `my-service`); the domain suffix is auto-appended from the Gateway.
- **mTLS** — Combine APIRule with an mTLS-enabled Istio Gateway for mutual TLS authentication.
- **Mixed strategies** — Protect some paths with `jwt` and leave health-check paths open with `noAuth` in the same APIRule.

---

### 📌 Via Kyma Dashboard (UI)

1. Go to your namespace → **Discovery and Network** → **API Rules**
2. Click **Create**
3. Fill in the **Name**, **Service Name**, **Host**, and configure **Rules** (methods + access strategy)
4. Click **Create** ✅

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

### ✅ Step 1: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to your SAP BTP subaccount → Kyma Runtime → **Modules**
- Add the **Istio** module if not already present.

---

### 🔁 Step 2: Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

#### For a Namespace (all Pods in the namespace):
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```
Or via **Kyma Dashboard**: Edit the namespace → toggle **Istio sidecar proxy injection** → Save.

#### For a Specific Deployment:
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```
Or via **Kyma Dashboard**: Edit the Deployment → toggle **Istio sidecar proxy injection** → Save.

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Namespace-level injection is disabled
> - The Pod has label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

### 🌐 Step 3: Expose Workloads via Istio Gateway

Istio provides **Ingress Gateways** to manage inbound traffic. Choose the right configuration based on your needs:

| TLS Mode | Default Kyma Domain | Custom Domain |
|---|---|---|
| **TLS** | Use pre-configured `kyma-gateway` (dev/test) | Recommended for production |
| **mTLS** | Secure B2B APIs, no DNS config needed | Strongest security for production B2B |

#### Option A: Use the Default Kyma Gateway (quick start)
The `kyma-system/kyma-gateway` is pre-configured and ready to use. Get your domain:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

#### Option B: Use Gateway API (Kubernetes-native approach)
1. Install Gateway API CRDs:
```bash
kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
{ kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -; }
```

2. Create a Gateway:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.kyma.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
```

3. Create an HTTPRoute:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.kyma.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```

---

### 🔒 Step 4: Secure Workloads

Combine Istio with the **API Gateway module** for secure workload exposure:
- Use **APIRule** custom resources to apply JWT authentication, rate limiting, etc.
- Configure **TLS** or **mTLS** Gateways for encrypted communication.
- Use **Network Policies** alongside Istio for fine-grained traffic control.

---

### 🗝️ Key Istio Use Cases in Kyma

| Use Case | How |
|---|---|
| **Service-to-service encryption** | Enable sidecar injection → mTLS is automatic |
| **Traffic management** | Use `VirtualService` and `DestinationRule` resources |
| **Ingress traffic** | Configure Istio Gateway + VirtualService or Gateway API |
| **Observability** | Istio provides metrics, traces, and access logs |
| **Security** | Use `AuthorizationPolicy` and `PeerAuthentication` resources |

---

> 💡 **Production Tip:** Avoid using the default wildcard Kyma domain in production. Set up a **custom domain with TLS or mTLS** for full control and stronger security.

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### 📋 Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### 🔐 Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider | Custom auth logic (e.g., OAuth2 Proxy) |

---

### 📄 Example APIRule YAMLs

#### 1. Open Endpoint (`noAuth`)
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service   # short host name; full domain is auto-appended from the Gateway
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service       # Kubernetes Service name
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

#### 2. JWT-Protected Endpoint (`jwt`) — Recommended
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: "https://my-identity-provider.com"
            jwksUri: "https://my-identity-provider.com/.well-known/jwks.json"
```

---

### 🛠️ Steps to Expose Your Endpoint

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply your APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Verify the APIRule is ready:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   # Expected output: Ready
   ```

4. **Access your endpoint:**
   Your service will be available at:
   `https://<host>.<cluster-domain>`

---

### 💡 Advanced Capabilities

- **Multiple workloads on the same host** — Route traffic to different Services based on paths/methods.
- **Short host names** — Use just a name (e.g., `my-service`); the domain suffix is auto-appended from the Gateway.
- **mTLS** — Combine APIRule with an mTLS-enabled Istio Gateway for mutual TLS authentication.
- **Mixed strategies** — Protect some paths with `jwt` and leave health-check paths open with `noAuth` in the same APIRule.

4. Click **Create** ✅

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to **Kyma Dashboard → Cluster Details → Modules**
- Enable the **Istio** module

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (recommended)
```bash
kubectl label namespace <your-namespace> istio-injection=enabled
```
All new Pods in this namespace will automatically get the Istio sidecar injected.

### For a Specific Deployment
```bash
kubectl patch -n <your-namespace> deployments/<your-deployment> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateways

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. Get your default domain:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

### Option B: Configure a Custom TLS Gateway (Production)
For production, set up a custom TLS Gateway with your own domain:
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-tls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: <your-tls-secret>
      hosts:
        - "myapp.example.com"
```

### Option C: Configure an mTLS Gateway (Secure B2B)
For mutual TLS (both client and server authenticate):
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-mtls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: MUTUAL
        credentialName: <your-mtls-secret>
      hosts:
        - "myapp.example.com"
```

## 4. 🚦 Expose Workloads Using Gateway API (Modern Approach)

Kyma's Istio module also supports the **Kubernetes Gateway API**:

```bash
# Install Gateway API CRDs (standard channel)
kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
{ kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -; }
```

Then create a **Gateway** and **HTTPRoute**:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```
