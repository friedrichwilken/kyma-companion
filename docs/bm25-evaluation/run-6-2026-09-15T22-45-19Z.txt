## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service Without Authentication (`noAuth`)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service   # Short host name; full domain is auto-resolved from the Gateway
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service       # Name of your Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service Secured with JWT

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: "https://my-identity-provider.com"
            jwksUri: "https://my-identity-provider.com/.well-known/jwks.json"
```

---

### Steps to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

---

### Advanced Capabilities

- 🔀 **Multiple workloads on the same host** — Route traffic to different services based on paths/methods.
- 🔒 **mTLS** — Combine APIRule with an mTLS-enabled Istio Gateway.
- 🌐 **Short host names** — Use just the service name; the domain suffix is auto-resolved from the Gateway.
- 🛡️ **Mixed strategies** — Protect some paths with `jwt` and leave others open with `noAuth` in the same APIRule.

---

> 💡 **Tip:** For production workloads, always prefer the `jwt` access strategy as it provides built-in, token-based authentication without additional infrastructure.

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to **Kyma Dashboard → Cluster Details → Modules**
- Enable the **Istio** module

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (recommended)
```bash
kubectl label namespace <your-namespace> istio-injection=enabled
```
All new Pods in this namespace will automatically get the Istio sidecar injected.

### For a Specific Deployment
```bash
kubectl patch -n <your-namespace> deployments/<your-deployment> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateways

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. Get your default domain:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

### Option B: Configure a Custom TLS Gateway (Production)
For production, set up a custom TLS Gateway with your own domain:
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-tls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: <your-tls-secret>
      hosts:
        - "myapp.example.com"
```

### Option C: Configure an mTLS Gateway (Secure B2B)
For mutual TLS (both client and server authenticate):
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-mtls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: MUTUAL
        credentialName: <your-mtls-secret>
      hosts:
        - "myapp.example.com"
```

---

## 4. 🚦 Expose Workloads Using Gateway API (Modern Approach)

Kyma's Istio module also supports the **Kubernetes Gateway API**:

```bash
# Install Gateway API CRDs (standard channel)
kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
{ kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -; }
```

Then create a **Gateway** and **HTTPRoute**:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```

- Go to **Kyma Dashboard → Modules** and add the **Istio** module.
- Or use the Kyma CLI / BTP Cockpit to enable it.

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a **sidecar proxy** (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```
Or via **Kyma Dashboard**: Select namespace → **Edit** → toggle **Istio sidecar proxy injection** → **Save**.

### For a Specific Deployment
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Injection is disabled at the namespace level
> - The Pod has `sidecar.istio.io/inject: "false"` label
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateway

Istio provides **Ingress Gateways** to expose your services. You have several options:

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. It uses a wildcard TLS domain.
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

### Option B: Configure a Custom TLS Gateway (Recommended for Production)
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-tls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: <your-tls-secret>
      hosts:
        - "myapp.example.com"
```

### Option C: Configure an mTLS Gateway (Strongest Security)
Use mTLS for B2B APIs where both client and server must present certificates.

### Option D: Use Kubernetes Gateway API (Modern Approach)
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: httpbin-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
    - name: http
      hostname: "myapp.kyma.example.com"
      port: 80
      protocol: HTTP
      allowedRoutes:
        namespaces:
          from: Same
```
Then create an **HTTPRoute** to route traffic to your service.

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service Without Authentication (`noAuth`)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service   # Short host name; full domain is auto-resolved from the Gateway
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service       # Name of your Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service Secured with JWT

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: "https://my-identity-provider.com"
            jwksUri: "https://my-identity-provider.com/.well-known/jwks.json"
```

---

### Steps to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

---

### Advanced Capabilities

- 🔀 **Multiple workloads on the same host** — Route traffic to different services based on paths/methods.
- 🔒 **mTLS** — Combine APIRule with an mTLS-enabled Istio Gateway.
- 🌐 **Short host names** — Use just the service name; the domain suffix is auto-resolved from the Gateway.
- 🛡️ **Mixed strategies** — Protect some paths with `jwt` and leave others open with `noAuth` in the same APIRule.

---

> 💡 **Tip:** For production workloads, always prefer the `jwt` access strategy as it provides built-in, token-based authentication without additional infrastructure.

## 🔷 Using Istio in SAP BTP, Kyma Runtime

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to your SAP BTP subaccount → Kyma Runtime → **Modules**
- Add the **Istio** module if not already present

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (recommended)
```bash
kubectl label namespace <your-namespace> istio-injection=enabled
```
Or via **Kyma Dashboard**: Edit the namespace → toggle **Istio sidecar proxy injection** → Save.

### For a Specific Deployment
```bash
kubectl patch -n <namespace> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ A Pod will **NOT** be injected if:
> - Injection is disabled at the namespace level
> - The Pod has `sidecar.istio.io/inject: "false"` label
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateway

Istio provides **Ingress Gateway** capabilities to expose services outside the cluster.

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. It uses a wildcard TLS domain.
> ⚠️ Not recommended for production — use a custom domain instead.

### Option B: Configure a Custom TLS Gateway
```yaml
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: my-tls-secret
    hosts:
    - "myapp.example.com"
```

### Option C: Use Kubernetes Gateway API (Modern Approach)
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
```
Then create an **HTTPRoute** to route traffic to your service.

## 4. 🔒 Secure Workloads with mTLS

For production B2B APIs, configure **mutual TLS (mTLS)** for stronger authentication:
- Both client and server present certificates
- Use `Configure an mTLS Gateway` for custom domain scenarios

## 🔴 Root Cause: PVC Stuck in `Pending` — Incompatible Access Mode

The deployment is not getting ready because the **Pod cannot be scheduled** — it's blocked waiting for its volume to be bound, and the volume binding is **failing**.

---

### 🔍 Problem Chain

| Layer | Status | Reason |
|---|---|---|
| **Deployment** | ❌ Not Available | `ProgressDeadlineExceeded` — timed out after 600s |
| **Pod** | ❌ Pending | `SchedulerError: running PreBind plugin "VolumeBinding": binding volumes: context deadline exceeded` |
| **PVC `example-pvc`** | ❌ Pending | Never bound to a PersistentVolume |

---

### 🧩 Why the PVC is Stuck

The PVC is configured with:
- **StorageClass:** `default` → backed by **AWS EBS** (`ebs.csi.aws.com`)
- **Access Mode:** `ReadWriteMany` (**RWX**)

⚠️ **AWS EBS does NOT support `ReadWriteMany`**. EBS volumes are block devices that can only be attached to **one node at a time**, so they only support `ReadWriteOnce` (**RWO**). The CSI provisioner cannot fulfill the RWX request, so the PVC stays `Pending` forever.

---

### ✅ Fix

Change the PVC's `accessModes` from `ReadWriteMany` to `ReadWriteOnce`.

> **Note:** PVC `spec` is immutable after creation. You must **delete the existing PVC** and recreate it with the correct access mode.

**Step 1 — Delete the existing PVC:**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: example-pvc
  namespace: test-deployment-4

  accessModes:
    - ReadWriteOnce        # ✅ Correct for AWS EBS
  resources:
    requests:
      storage: 1Gi
  storageClassName: default
  volumeMode: Filesystem
```
