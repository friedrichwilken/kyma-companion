---

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service with No Auth (Open Endpoint)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service          # Short host name (domain suffix auto-appended from Gateway)
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service      # Name of the Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service with JWT Authentication (Recommended)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: "https://my-identity-provider.com"
            jwksUri: "https://my-identity-provider.com/.well-known/jwks.json"
```

---

### How to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<YOUR_CLUSTER_DOMAIN>
   ```

---

### Key Capabilities

- 🔀 **Multiple workloads on the same host** — route traffic to different services based on paths/methods
- 🔒 **Mixed auth per path** — e.g., `jwt` on `/api/*` and `noAuth` on `/health`
- 🌐 **Short host names** — just provide the subdomain; the full domain is auto-resolved from the Gateway
- 🔐 **mTLS support** — combine with an mTLS-enabled Istio Gateway for mutual TLS

---

> 💡 **Tip:** For production workloads, always prefer the `jwt` access strategy to ensure token-based authentication without additional infrastructure overhead.

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

### ✅ Prerequisites

1. **Add the Istio module** to your Kyma cluster via the Kyma dashboard or CLI:
   - Go to your Kyma cluster → **Modules** → Enable **Istio**.

---

### 1️⃣ Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy into your Pods. You can enable this at the **namespace** or **Deployment** level.

#### For a Namespace:
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```
> All new Pods in this namespace will automatically get the Istio sidecar injected.

#### For a Specific Deployment:
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

### 2️⃣ Expose Workloads Using Istio Gateways

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

#### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. Get your default domain:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

#### Option B: Configure a Custom TLS Gateway (Recommended for Production)
Use your own domain with a TLS or mTLS Gateway for full control and stronger security.

| TLS Mode | Default Kyma Domain | Custom Domain |
|----------|-------------------|---------------|
| **TLS** | Custom TLS Gateway (no DNS config needed) | ✅ Recommended for production |
| **mTLS** | Secure B2B APIs (no DNS config needed) | ✅ Strongest security for B2B |

---

### 3️⃣ Expose a Workload Using Gateway API (Kubernetes-native)

Kyma's Istio module also supports the **Kubernetes Gateway API**:

```bash
# Install Gateway API CRDs (standard channel)
kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
{ kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -; }
```

**Create a Gateway:**
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.kyma.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
```

**Create an HTTPRoute:**
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-httproute
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.kyma.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service with No Auth (Open Endpoint)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service          # Short host name (domain suffix auto-appended from Gateway)
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service      # Name of the Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service with JWT Authentication (Recommended)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: "https://my-identity-provider.com"
            jwksUri: "https://my-identity-provider.com/.well-known/jwks.json"
```

---

### How to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<YOUR_CLUSTER_DOMAIN>
   ```

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

### ✅ Step 1: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to the **Kyma Dashboard → Cluster Details → Modules**
- Enable the **Istio** module

### 🔁 Step 2: Enable Sidecar Proxy Injection

Istio works by injecting a **sidecar proxy** (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

#### For a Namespace:
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```
Or via **Kyma Dashboard**: Edit the namespace → toggle **Istio sidecar proxy injection** → Save.

#### For a Deployment:
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```
Or via **Kyma Dashboard**: Edit the Deployment → toggle **Istio sidecar proxy injection** → Save.

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

### 🌐 Step 3: Expose Workloads Using Istio Gateways

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

#### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```
> ⚠️ Not recommended for production — it uses a wildcard domain with simple TLS.

#### Option B: Configure a Custom TLS Gateway (Recommended for Production)
Choose based on your needs:

| TLS Mode | Domain | Recommendation |
|----------|--------|----------------|
| TLS | Default Kyma domain | Dev/test with Gateway isolation |
| TLS | Custom domain | ✅ Recommended for production |
| mTLS | Default Kyma domain | Secure B2B APIs, no DNS setup needed |
| mTLS | Custom domain | ✅ Strongest security for production B2B |

### 🚦 Step 4: Expose Workloads Using Gateway API (Modern Approach)

Kyma's Istio module also supports the **Kubernetes Gateway API**:

1. **Install Gateway API CRDs:**
   ```bash
   kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
   { kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -; }
   ```

2. **Create a Gateway:**
   ```yaml
   apiVersion: gateway.networking.k8s.io/v1
   kind: Gateway
   metadata:
     name: my-gateway
     namespace: my-namespace
   spec:
     gatewayClassName: istio
     listeners:
     - name: http
       hostname: "myapp.kyma.example.com"
       port: 80
       protocol: HTTP
       allowedRoutes:
         namespaces:
           from: Same
   ```

3. **Create an HTTPRoute:**
   ```yaml
   apiVersion: gateway.networking.k8s.io/v1
   kind: HTTPRoute
   metadata:
     name: my-route
     namespace: my-namespace
   spec:
     parentRefs:
     - name: my-gateway
     hostnames: ["myapp.kyma.example.com"]
     rules:
     - matches:
       - path:
           type: PathPrefix
           value: /
       backendRefs:
       - name: my-service
         port: 8080
   ```
