---

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service Without Authentication (`noAuth`)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service          # Short host name; full domain is auto-resolved
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service      # Name of the Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service Secured with JWT

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: https://my-identity-provider.com
            jwksUri: https://my-identity-provider.com/.well-known/jwks.json
```

---

### Steps to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

---

### 💡 Key Tips

- **Short host names** are supported — the domain suffix is automatically taken from the referenced Istio Gateway.
- You can **expose multiple workloads on the same host** by routing traffic to different Services based on paths and HTTP methods.
- For **mTLS**, combine an APIRule with an mTLS-enabled Istio Gateway.
- The workload (Pod/Service) must be **part of the Istio service mesh** (sidecar injection enabled) when using `jwt` or `extAuth`.

## 🔷 Using Istio in SAP BTP, Kyma Runtime

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to your SAP BTP subaccount → Kyma Runtime → **Modules**
- Add the **Istio** module if not already present

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (all Pods in the namespace):

**Via Kyma Dashboard:**
1. Select the namespace → **Edit**
2. Toggle **Istio sidecar proxy injection** → **Save**

**Via kubectl:**
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```

### For a Single Deployment:

**Via kubectl:**
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateway

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. It uses a wildcard TLS domain.

> ⚠️ Not recommended for production — use a custom domain instead.

### Option B: Configure a Custom TLS Gateway (Recommended for Production)
```yaml
apiVersion: networking.istio.io/v1alpha3
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: <your-tls-secret>
    hosts:
    - "myapp.example.com"
```

### Option C: Use Kubernetes Gateway API (Modern Approach)
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
```

Then create an **HTTPRoute** to route traffic to your service:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```

---

## 4. 🔒 Secure Workloads with mTLS

For B2B or production APIs, configure **mutual TLS (mTLS)** to require client certificates:
- Use `mode: MUTUAL` in your Gateway TLS configuration
- Provide a `caCertificates` reference for client certificate validation

---

For the most secure and feature-rich setup, use **Istio together with the API Gateway module**:
- Create **APIRule** resources to expose and secure workloads with JWT authentication

## 3. 🌐 Expose Workloads Using Istio Gateway

Istio provides **Ingress Gateways** to expose your services. You have several options:

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. It uses a wildcard TLS domain.
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

### Option B: Configure a Custom TLS Gateway (Recommended for Production)
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-tls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: <your-tls-secret>
      hosts:
        - "myapp.example.com"
```

### Option C: Configure an mTLS Gateway (Strongest Security)
Use mTLS for B2B APIs where both client and server must present certificates.

### Option D: Use Kubernetes Gateway API (Modern Approach)
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: httpbin-gateway
  namespace: <your-namespace>

  gatewayClassName: istio

      port: 80
      protocol: HTTP
      allowedRoutes:
        namespaces:
          from: Same
```
Then create an **HTTPRoute** to route traffic to your service.

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service Without Authentication (`noAuth`)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service          # Short host name; full domain is auto-resolved
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service      # Name of the Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service Secured with JWT

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: https://my-identity-provider.com
            jwksUri: https://my-identity-provider.com/.well-known/jwks.json
```

---

### Steps to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

---

### 💡 Key Tips

- **Short host names** are supported — the domain suffix is automatically taken from the referenced Istio Gateway.
- You can **expose multiple workloads on the same host** by routing traffic to different Services based on paths and HTTP methods.
- For **mTLS**, combine an APIRule with an mTLS-enabled Istio Gateway.
- The workload (Pod/Service) must be **part of the Istio service mesh** (sidecar injection enabled) when using `jwt` or `extAuth`.

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a **sidecar proxy** (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```
Or via **Kyma Dashboard**: Select the namespace → **Edit** → toggle **Istio sidecar proxy injection** → **Save**.

### For a Specific Deployment
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \

```
Or via **Kyma Dashboard**: Navigate to the Deployment → **Edit** → toggle **Istio sidecar proxy injection** → **Save**.

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

| TLS Mode | Domain | Use Case |

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:

  gatewayClassName: istio

    protocol: HTTP

        from: Same
```

## 🔴 Root Cause: Missing RBAC Role `pod-reader`

The pod runs a single command:
```sh
kubectl get pods
```

It uses the **ServiceAccount `test-pod-1-sa`**, which is bound via `test-pod-1-binding` to a **Role named `pod-reader`** — but **that Role does not exist** in the `test-pod-1` namespace.

This means the ServiceAccount has **no permissions** to call `kubectl get pods`, causing the command to fail with **exit code 1**.

## ✅ Fix: Create the Missing `pod-reader` Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1

  name: pod-reader
  namespace: test-pod-1

    verbs: ["get", "list", "watch"]
```

```bash
kubectl apply -f pod-reader-role.yaml
```
