## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service Without Authentication (`noAuth`)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service          # Short host name; full domain is auto-resolved
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service      # Name of the Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service Secured with JWT

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: https://my-identity-provider.com
            jwksUri: https://my-identity-provider.com/.well-known/jwks.json
```

---

### How to Apply

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply the APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Check the status:**
   ```bash
   kubectl get apirule my-service -n my-namespace -o jsonpath='{.status.state}'
   ```
   It should return `Ready`.

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

---

### Advanced Capabilities

| Feature | Description |
|---|---|
| **Short host names** | Use just `my-service` instead of the full FQDN |
| **Multiple workloads on one host** | Route traffic to different services based on paths/methods |
| **mTLS** | Combine APIRule with an mTLS-enabled Istio Gateway |
| **Mixed strategies** | Use `jwt` on sensitive paths and `noAuth` on health check paths |

---

### 💡 Recommendation

For production workloads, use the **`jwt`** access strategy with **SAP Cloud Identity Services** as the identity provider. It provides built-in, token-based authentication without additional infrastructure.

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to **Kyma Dashboard → Cluster Details → Modules**
- Enable the **Istio** module

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (recommended)
```bash
kubectl label namespace <your-namespace> istio-injection=enabled
```
All new Pods in this namespace will automatically get the Istio sidecar injected.

### For a Specific Deployment
```bash
kubectl patch -n <your-namespace> deployments/<your-deployment> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateway

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. It uses a wildcard TLS domain.

```bash
# Check your default Kyma domain
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

### Option B: Configure a Custom TLS Gateway (Production)
For production, set up a custom domain with TLS:
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: <your-tls-secret>
    hosts:
    - "myapp.example.com"
```

### Option C: Use Kubernetes Gateway API (Modern Approach)
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
```
Then create an `HTTPRoute` to route traffic to your service.

---

## 4. 🔒 Secure Workloads with mTLS

For B2B or production APIs, configure **mutual TLS (mTLS)** to require both server and client certificates:
- Use `Configure an mTLS Gateway` for the strongest security
- Both server and client must present valid certificates

---

## 5. 🛡️ Secure Workload Exposure with APIRule

Combine Istio with the **API Gateway module** to expose and secure workloads using JWT:
```yaml
apiVersion: gateway.kyma-project.io/v1beta1
kind: APIRule
metadata:
  name: my-apirule
  namespace: <your-namespace>
spec:
  gateway: kyma-system/kyma-gateway
  host: myapp.<your-kyma-domain>
  service:
    name: my-service
    port: 8080
  rules:
  - path: /.*
    methods: ["GET"]
    accessStrategies:
    - handler: jwt
      config:
        jwks_urls:
        - <your-jwks-url>
```

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider (e.g., OAuth2 Proxy) | Custom auth logic |

---

### Example 1: Expose a Service Without Authentication (`noAuth`)

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service          # Short host name; full domain is auto-resolved
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service      # Name of the Kubernetes Service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

---

### Example 2: Expose a Service Secured with JWT

```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-secure-service
  namespace: my-namespace
spec:
  hosts:
    - my-secure-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-secure-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: https://my-identity-provider.com
            jwksUri: https://my-identity-provider.com/.well-known/jwks.json
```

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (recommended)
```bash
kubectl label namespace <your-namespace> istio-injection=enabled
```
All new Pods in this namespace will automatically get the Istio sidecar injected.

### For a Specific Deployment
```bash
kubectl patch -n <your-namespace> deployments/<your-deployment> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

## 3. 🌐 Expose Workloads Using Istio Gateways

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. Get your default domain:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```

### Option B: Configure a Custom TLS Gateway (Production)
For production, set up a custom TLS Gateway with your own domain:
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-tls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: <your-tls-secret>
      hosts:
        - "myapp.example.com"
```

### Option C: Configure an mTLS Gateway (Secure B2B)
For mutual TLS (both client and server authenticate):
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-mtls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: MUTUAL
        credentialName: <your-mtls-secret>
      hosts:
        - "myapp.example.com"
```

```bash
# Install Gateway API CRDs (standard channel)
```

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.example.com"]

  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```
