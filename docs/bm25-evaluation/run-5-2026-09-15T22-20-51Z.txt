---

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### 📋 Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### 🔐 Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider | Custom auth logic (e.g., OAuth2 Proxy) |

---

### 📄 Example APIRule YAMLs

#### 1. Open Endpoint (`noAuth`)
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service   # short host name; full domain is appended automatically
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service       # Kubernetes Service name
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

#### 2. JWT-Protected Endpoint (`jwt`) — Recommended
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: https://<your-identity-provider>
            jwksUri: https://<your-identity-provider>/.well-known/jwks.json
```

---

### 🛠️ Steps to Expose Your Endpoint

1. **Get your cluster domain:**
   ```bash
   kubectl get gateway -n kyma-system kyma-gateway \
     -o jsonpath='{.spec.servers[0].hosts[0]}'
   ```

2. **Apply your APIRule:**
   ```bash
   kubectl apply -f apirule.yaml
   ```

3. **Verify the APIRule is ready:**
   ```bash
   kubectl get apirule my-service -n my-namespace \
     -o jsonpath='{.status.state}'
   # Expected output: Ready
   ```

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

---

### 💡 Advanced Capabilities

- **Multiple workloads on the same host** — Route traffic to different services based on paths/methods.
- **Short host names** — Use just the service name; the domain suffix is auto-appended from the Gateway.
- **mTLS** — Combine APIRule with an mTLS-enabled Istio Gateway for mutual TLS.
- **Mixed strategies** — Protect some paths with `jwt` and leave health-check paths open with `noAuth` in the same APIRule.

---

### 🖥️ Using Kyma Dashboard (Busola)

1. Go to your namespace → **Discovery and Network** → **API Rules**
2. Click **Create**
3. Fill in the **Name**, **Service Name**, **Host**, and **Rules** (methods + access strategy)
4. Click **Create** — your endpoint is live!

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

### ✅ Step 1: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to the Kyma Dashboard → **Modules** → Add **Istio**.

---

### 🔁 Step 2: Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy into your Pods. You can enable this at the **namespace** or **Deployment** level.

#### For a Namespace:
```bash
kubectl label namespace <namespace-name> istio-injection=enabled
```
Or via Kyma Dashboard: **Namespace → Edit → Enable Istio Sidecar Proxy Injection → Save**.

#### For a Deployment:
```bash
kubectl patch -n <namespace-name> deployments/<deployment-name> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

### 🌐 Step 3: Expose Workloads via Istio Gateway

Istio Gateways manage inbound/outbound traffic at the edge of the service mesh.

#### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use. It's a wildcard TLS gateway on the default Kyma domain.

> ⚠️ Not recommended for production — use a custom domain instead.

#### Option B: Configure a Custom TLS Gateway (Recommended for Production)
```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-tls-gateway
  namespace: <your-namespace>
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: <your-tls-secret>
      hosts:
        - "myapp.example.com"
```

#### Option C: Configure an mTLS Gateway (Strongest Security)
Use mTLS for B2B APIs where both client and server must present certificates.

---

### 🚦 Step 4: Use Gateway API (Modern Approach)

Kyma's Istio module also supports the **Kubernetes Gateway API** for a vendor-neutral way to expose workloads:

```bash
# Install Gateway API CRDs (standard channel)
kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
{ kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -; }
```

Then create a **Gateway** and **HTTPRoute**:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: <your-namespace>
spec:
  gatewayClassName: istio
  listeners:
  - name: http
    hostname: "myapp.example.com"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Same
```

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-httproute
  namespace: <your-namespace>
spec:
  parentRefs:
  - name: my-gateway
  hostnames: ["myapp.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: <your-service>
      port: <your-port>
```

Combine Istio with the **API Gateway module** to securely expose workloads:
- Use **APIRule** custom resources to apply JWT authentication.
- Set up **Network Policies** to restrict traffic between Pods.
- Use **mTLS** for service-to-service communication within the mesh.

## What is Kyma?

**SAP BTP, Kyma runtime** is a fully managed, cloud-native **Kubernetes application runtime** based on the open-source [Kyma project](https://kyma-project.io/). It is part of the **SAP Business Technology Platform (SAP BTP)** and is designed to help developers build, extend, and integrate applications in a cloud-native way.

---

### 🔑 Key Highlights

| Aspect | Description |
|---|---|
| **Foundation** | Built on top of **Kubernetes**, providing a production-grade container orchestration platform |
| **Managed Service** | Fully managed by SAP on hyperscalers (AWS, Azure, GCP), so you don't need to manage the underlying infrastructure |
| **Open Source** | Based on the open-source Kyma project, ensuring transparency and community-driven innovation |
| **Extensibility** | Designed to extend SAP applications (like SAP S/4HANA, SAP Commerce Cloud) with custom logic and integrations |

---

### 🧩 Core Capabilities (via Modules)

Kyma is **modular** — you can enable only the capabilities you need:

- **Serverless** — Run functions-as-a-service (FaaS) using Kyma Functions
- **Eventing** — Event-driven architecture to connect SAP and external systems
- **API Gateway** — Expose services securely via API Rules (powered by Istio & ORY)
- **Application Connector** — Integrate external systems (on-premise or cloud) with Kyma workloads
- **Service Mesh (Istio)** — Secure, observe, and control service-to-service communication
- **Observability** — Tracing, logging, and monitoring pipelines
- **NATS / Eventing** — Reliable event delivery between services

---

### 🛠️ Interfaces

Kyma provides two main interfaces:
1. **Kyma Dashboard (Busola)** — A web-based UI for managing Kubernetes and Kyma resources visually
2. **Kyma CLI** — A command-line tool for tasks like deploying functions, managing modules, etc.

---

### 🎯 Primary Use Cases

- **Extending SAP applications** with custom microservices or serverless functions
- **Integrating external systems** with SAP BTP services
- **Building cloud-native applications** on a managed Kubernetes platform
- **Event-driven integrations** between SAP and non-SAP systems

---

In short, **Kyma is SAP's opinionated, managed Kubernetes runtime** that combines the power of cloud-native technologies (Kubernetes, Istio, NATS, etc.) with SAP's extensibility and integration ecosystem. It lets developers focus on building business logic rather than managing infrastructure.

## 🚀 Exposing an Endpoint in Kyma with APIRule

### What is an APIRule?

An **APIRule** is a Kyma custom resource that makes a Kubernetes Service reachable from outside the cluster. It automatically translates into Istio resources (`VirtualService`, `AuthorizationPolicy`) — no need to manage those manually.

---

### 📋 Prerequisites

Make sure the following Kyma modules are enabled in your cluster:
- **Istio**
- **API Gateway**

---

### 🔐 Access Strategies

You can choose one of three access strategies per path:

| Strategy | Description | Use Case |
|---|---|---|
| `noAuth` | Open endpoint, no authentication | Dev/testing or public data |
| `jwt` | Protect with JSON Web Tokens | ✅ Recommended for most scenarios |
| `extAuth` | Delegate auth to an external provider | Custom auth logic (e.g., OAuth2 Proxy) |

---

### 📄 Example APIRule YAMLs

#### 1. Open Endpoint (`noAuth`)
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service   # short host name; full domain is appended automatically
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service       # Kubernetes Service name
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST", "PUT", "DELETE"]
      noAuth: true
```

#### 2. JWT-Protected Endpoint (`jwt`) — Recommended
```yaml
apiVersion: gateway.kyma-project.io/v2
kind: APIRule
metadata:
  name: my-service
  namespace: my-namespace
spec:
  hosts:
    - my-service
  gateway: kyma-system/kyma-gateway
  service:
    name: my-service
    namespace: my-namespace
    port: 80
  rules:
    - path: /*
      methods: ["GET", "POST"]
      jwt:
        authentications:
          - issuer: https://<your-identity-provider>
            jwksUri: https://<your-identity-provider>/.well-known/jwks.json
```


3. **Verify the APIRule is ready:**
   ```bash
   kubectl get apirule my-service -n my-namespace \
     -o jsonpath='{.status.state}'
   # Expected output: Ready
   ```

4. **Access your endpoint:**
   ```
   https://my-service.<your-cluster-domain>
   ```

## 🔷 Using Istio in Kyma

Istio is a powerful service mesh module in Kyma that provides traffic management, security, and observability for your workloads. Here's how to get started:

---

## 1. ✅ Prerequisites: Add the Istio Module

Before using Istio, make sure the **Istio module is enabled** in your Kyma cluster:
- Go to **Kyma Dashboard → Cluster Details → Modules**
- Enable the **Istio** module

---

## 2. 💉 Enable Sidecar Proxy Injection

Istio works by injecting a sidecar proxy (Envoy) into your Pods. You can enable this at the **namespace** or **Deployment** level.

### For a Namespace (recommended)
```bash
kubectl label namespace <your-namespace> istio-injection=enabled
```
All new Pods in this namespace will automatically get the Istio sidecar injected.

### For a Specific Deployment
```bash
kubectl patch -n <your-namespace> deployments/<your-deployment> \
  -p '{"spec":{"template":{"metadata":{"labels":{"sidecar.istio.io/inject":"true"}}}}}'
```

> ⚠️ **Note:** A Pod will **NOT** be injected if:
> - Sidecar injection is disabled at the namespace level
> - The Pod has the label `sidecar.istio.io/inject: "false"`
> - The Pod spec contains `hostNetwork: true`

---

## 3. 🌐 Expose Workloads Using Istio Gateway

Istio provides **Gateways** to manage inbound/outbound traffic. You have several options:

### Option A: Use the Default Kyma Gateway (Quick Start / Dev)
The default gateway `kyma-system/kyma-gateway` is pre-configured and ready to use:
```bash
kubectl get gateway -n kyma-system kyma-gateway \
  -o jsonpath='{.spec.servers[0].hosts[0]}'
```
> ⚠️ Not recommended for production — it uses a wildcard domain with simple TLS.

### Option B: Configure a Custom TLS Gateway (Production)
For production, set up a custom TLS Gateway with your own domain:
```yaml
apiVersion: networking.istio.io/v1alpha3

  name: my-tls-gateway
  namespace: <your-namespace>

  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
```
